## 💡 Зачем это нужно

Баг пагинации проходит мимо любых проверок здоровья сервиса. Каждая страница отвечает `200 OK`,
цикл завершается, в логах чисто, а в выгрузке не хватает четырёхсот строк. Вы узнаёте об этом
через несколько недель, когда кто-то сверяет итоги, а запись обмена к тому времени давно удалена.

Интеграционные тесты ходят в живой API и поэтому флакают. Логи пишут каждый запрос отдельной
строкой, а баг сидит между двумя строками: страница 3 отправила токен, которого страница 2 не
возвращала. Такое можно найти, читая HAR глазами, пока в трейсе не наберётся десяток страниц.

PageTrace читает запись, которая у вас уже есть, и сообщает, что по ней можно доказать.

| Что вам говорят | Что PageTrace скажет по трейсу |
| --------------- | ------------------------------ |
| "В выгрузке не хватает строк" | запрашивалась ли страница с токеном, которого предыдущая не возвращала; вернулась ли последовательность запросов в прежнее состояние; не оборвалась ли запись раньше времени |
| "Задача никак не закончится" | застрял ли курсор на одном значении или запросы вернулись в состояние, где уже были |
| "Ниже по потоку приходят дубли" | какой идентификатор элемента встретился на каких двух страницах |
| "У них сломан API" | позволяет ли трейс обвинить хоть одну из сторон (часто не позволяет) |

> [!IMPORTANT]
> **Правило: PageTrace никогда не утверждает больше, чем доказывает трейс.**
> Каждая находка указывает свою уверенность и перечисляет наблюдения, на которых стоит. Числовых
> оценок уверенности в инструменте нет. Если для проверки в трейсе не хватает данных, вы получите
> `INSUFFICIENT_EVIDENCE` и имя флага, который нужно задать.

Обычные сценарии: регрессионный тест в CI, который падает на доказанном дефекте, или инцидент,
где HAR от коллеги остался единственным свидетельством. Ещё PageTrace пригодится перед интеграцией
с чужим API, когда вы хотите отправить поставщику находки без преувеличений.

## ⚡ Посмотреть за 30 секунд

```bash
uv run pagetrace check examples/broken-cursor.jsonl
```

```
broken-cursor.jsonl: 3 pages, preset cursor

PROVEN ERROR CURSOR_CONTINUATION_MISMATCH [INV-CURSOR-001] pages 1, 2
  Page 2 was requested with a continuation token that page 1 did not return.
  page[1].response.next_cursor = "eyJvIjo0fQ"
  page[2].request.cursor = "eyJvIjozfQ"

PROVEN WARNING DUPLICATE_ITEM_ACROSS_PAGES [INV-ITEM-001] pages 1, 2
  An item observed on page 1 was observed again on page 2; its identity is in the evidence below. That the same item appears twice is a fact; whether it means overlapping pages depends on a uniqueness contract this trace does not contain.
  page[1].items[0].id = 3
  page[2].items[0].id = 3

2 proven, 0 suspicious, 0 insufficient evidence
```

Команда завершается с кодом 1. Вторая находка сообщает о дубликате и на этом останавливается. В
трейсе нет контракта уникальности, поэтому PageTrace не называет дубликат багом пагинации.

`examples/clean-cursor.jsonl` содержит тот же прогон без дефектов и завершается с кодом 0.

## ⚡ Установка

```bash
pip install pagetrace
```

`pipx install pagetrace` и `uv tool install pagetrace` ставят его как отдельную команду.

Чтобы запустить примеры, склонируйте репозиторий и используйте [uv](https://docs.astral.sh/uv/):

```bash
uv sync
uv run pagetrace check examples/broken-cursor.jsonl
```

## 📼 Как записать трейс

В трейсе JSONL на каждую пару запрос-ответ приходится одна строка с JSON-объектом, в том порядке,
в каком вы их записали:

```json
{"v": 1, "seq": 0, "request": {"method": "GET", "url": "https://api.example.com/v1/items?limit=2"}, "response": {"status": 200, "headers": {"content-type": "application/json"}, "body": {"items": [{"id": 1, "name": "item-1"}, {"id": 2, "name": "item-2"}], "next_cursor": "eyJvIjoyfQ", "has_more": true, "total": 5}}}
```

Поля `v` и `response.status` обязательны. `seq` можно не указывать, PageTrace ориентируется на
порядок строк. Полные правила: [specs/formats/jsonl-v1.md](specs/formats/jsonl-v1.md).

<details>
<summary><b>Или выгрузите HAR из браузера</b>, это работает с любым API, который открывается в браузере</summary>

<br>

В DevTools откройте вкладку Network, пролистайте страницы результатов и сохраните список запросов
как HAR. В файл попадут ещё скрипты, картинки и шрифты страницы, поэтому оставьте только вызовы
API:

```bash
uv run pagetrace check your-capture.har --url-filter /v1/items
```

PageTrace отбрасывает запросы `OPTIONS` и `HEAD` до нумерации страниц, и CORS-предзапрос не
выглядит как клиент, застрявший на одной странице.

</details>

> [!WARNING]
> HAR-файл содержит действующие учётные данные. PageTrace оставляет один заголовок ответа и не
> печатает тела, но в файле на вашем диске по-прежнему лежит заголовок `Authorization`. Храните
> файл как пароль и не прикладывайте его к публичным issue.

## 🎯 Пресеты

Селекторы пишутся на JSONPath по [RFC 9535](https://www.rfc-editor.org/rfc/rfc9535.html). Если
дефолт пресета ни с чем не совпал, PageTrace записывает значение как ненайденное и не делает по
нему выводов.

| Пресет | Селекторы по умолчанию | Подходит |
| ------ | ---------------------- | -------- |
| `cursor` <sub>по умолчанию</sub> | `--cursor $.query.cursor` `--next $.next_cursor` `--items $.items` `--id $.id` `--total $.total` `--has-more $.has_more` | API, которые возвращают непрозрачный токен продолжения |
| `page` | `--page $.query.page`, плюс те же items / id / total / has-more | номера страниц, с 0 или с 1 |
| `offset` | `--offset $.query.offset`, плюс те же items / id / total / has-more | смещение и лимит |
| `link` | только items / id / total / has-more; следующая страница берётся из HTTP-заголовка `Link` | `rel="next"` в заголовке Link (RFC 8288) |

> [!TIP]
> Каждый дефолт можно заменить своим флагом. `uv run pagetrace check --help` выводит дефолты по
> пресетам. Если находка говорит `INSUFFICIENT_EVIDENCE`, в её сообщении указан нужный флаг.

## 📊 Уверенность, серьёзность, коды выхода

У каждой находки две отдельные оценки. Уверенность показывает, насколько трейс её подтверждает, а
серьёзность показывает, насколько она важна, если верна. Ни одна из них не вероятность.

| Уверенность | Значение |
| ----------- | -------- |
| `PROVEN` | трейс это показывает, и предпосылки выполнены |
| `SUSPICIOUS` | трейс подходит под дефект, но подходит и под безобидное объяснение |
| `INSUFFICIENT_EVIDENCE` | селектор или трейс не дали того, что нужно проверке |

| Выход | Значение |
| ----- | -------- |
| `0` | нет находки, которая одновременно доказана и серьёзна |
| `1` | хотя бы одна находка `PROVEN` имеет серьёзность `ERROR` |
| `2` | некорректный вход или конфигурация |

Для кода выхода 1 нужны обе оценки. Дубликат элемента между страницами имеет оценку
`PROVEN WARNING` и сборку не роняет. Находка не называет дубликат багом, а упавшая сборка
утверждала бы это за неё. Если сборка краснеет из-за того, что может оказаться артефактом кэша,
команда перестанет обращать внимание на инструмент.

В CI читайте JSON-вывод. Формат терминального вывода PageTrace стабильным не обещает:

```bash
uv run pagetrace check examples/broken-cursor.jsonl --format json --output report.json
```

## 🧭 Чего он вам не скажет

На эти вопросы PageTrace не отвечает, даже когда трейс вроде бы подсказывает ответ.

- Завершается ли пагинация. Конечный трейс может показать, что последовательность запросов
  вернулась в прежнее состояние, и `INV-CURSOR-003` сообщает об этом. Если цикл возвращается в
  состояние страницы 0 после `null`-курсора, находка понижается до `SUSPICIOUS`: два прогона,
  сохранённые в один файл, выглядят так же.
- Пропали ли записи. `INV-TOTAL-001` сравнивает объявленный итог с идентификаторами, которые
  встретились в трейсе, и в её сообщении нет слов "потеряно N записей". PageTrace не может знать,
  считает ли `total` тот же набор элементов, менялись ли данные во время записи и применялись ли к
  обоим одни и те же фильтры.
- Кто виноват. `INV-CONT-001` и `INV-TRACE-001` сообщают, что трейс закончился, когда сервер ещё
  предлагал следующие страницы. Они не обвиняют ни API, ни клиента, ни того, кто делал запись.
- Что означает дубликат. Находка сообщает о дубликате. Чтобы назвать его багом, нужен контракт
  уникальности, а в трейсе его нет.
- Что-либо по странице, которую PageTrace не смог прочитать. Проверки, читающие тело ответа,
  пропускают ответы вне 2xx, а `INV-TRACE-002` один раз сообщает о пропущенных запросах. Трейс из
  одних ошибок не сойдёт за чистый.
- Что-либо по селектору, который не разрешился. Если селектор ничего не нашёл, нашёл два значения
  или указал на объект, результат будет `INSUFFICIENT_EVIDENCE` с именем флага. JSON `null`
  считается наблюдением: сервер сообщил, что следующей страницы нет.
- Различаются ли `5` и `"5"`. PageTrace сравнивает значения как текст, потому что параметр
  запроса передаёт только текст. Ещё он не считает `1` или `"true"` значением `has_more`, для
  этого нужен JSON-булев тип.

В [specs/invariants.md](specs/invariants.md) перечислены утверждения всех одиннадцати инвариантов
и условия, при которых каждый детектор молчит. Инструмент следует этому файлу как контракту.

## 🔒 Безопасность

Считайте трейс HAR или JSONL недоверенными входными данными с секретами внутри. Парсеры оставляют
один заголовок ответа, `link`, потому что его читает пресет link. `authorization`, `cookie` и
остальные заголовки они отбрасывают до построения модели. Детекторы и рендереры не получают сырых
тел, поэтому в отчёте есть только выбранные вами значения, с экранированными управляющими
символами и обрезанными длинными строками. PageTrace ограничивает длину строки и размер
декодированного тела, сообщает о слишком большом входе ошибкой использования вместо трейсбека и
не содержит сетевого кода или сетевых зависимостей. Таблица угроз и лимиты:
[docs/security.md](docs/security.md).

## 📈 Производительность

Замер 2026-09-11 на рабочей машине с Windows 11 и CPython 3.12.6, по одному прогону на форму.
Память здесь означает пиковое выделение Python по данным `tracemalloc`. Повторный прогон сдвинет
последнюю цифру, так что смотрите на соотношения.

| Форма | Страниц | Элементов | Секунд | Пик, MiB |
| ----- | ------: | --------: | -----: | -------: |
| широкая | 1 000 | 100 000 | 2.6 | 16.1 |
| очень широкая | 1 000 | 1 000 000 | 20.9 | 156.8 |
| десять тысяч страниц | 10 000 | 1 000 000 | 28.3 | 142.8 |
| сто тысяч страниц | 100 000 | 5 000 000 | 120.8 | 715.4 |

> [!NOTE]
> PageTrace не укладывается в три цели по времени, и проект оставляет их целями. 1k страниц /
> 100k id должны занимать 2 с, а занимают 2.6 с. 10k / 1M должны занимать 10 с, а занимают 28.3 с,
> примерно втрое дольше. Растянутая цель для 100k / 5M составляет 60 с, прогон занял 120.8 с,
> примерно вдвое дольше. Пиковая память осталась в пределах обоих лимитов: 142.8 MiB при лимите
> 512 MiB и 715.4 MiB при лимите 2 GiB. Полная таблица и разбор: [docs/performance.md](docs/performance.md).

## 🛠 Участие в разработке

```bash
uv run ruff check . && uv run ruff format --check . && uv run pyright && uv run pytest
```

Все 425 тестов проходят локально при покрытии по ветвям 98.97%, на Python 3.11, 3.12, 3.13 и 3.14
под Windows. Основную проверку корректности несёт property-набор в `tests/property/`: ни один
сгенерированный валидный трейс не должен давать находку `PROVEN`, а каждый мутационный оператор
должен срабатывать ровно на одном детекторе. Мутационный счёт против юнит-тестов на 2026-09-12
составил 77.9%, выжившие мутанты вручную разобраны в [docs/testing.md](docs/testing.md). mutmut не
работает под Windows, поэтому этот прогон шёл в контейнере с Linux.

Новый детектор начинается с записи в [specs/invariants.md](specs/invariants.md) с условиями, при
которых он молчит. Потом пишется тестовый оракул, код идёт последним. В
[CONTRIBUTING.md](CONTRIBUTING.md) описаны процесс и критерии готовности, в
[AGENTS.md](AGENTS.md) те же правила для кодовых агентов. Подробнее:
[docs/architecture.md](docs/architecture.md), [docs/testing.md](docs/testing.md),
[docs/compatibility.md](docs/compatibility.md), [docs/adr/](docs/adr/) и
[CHANGELOG.md](CHANGELOG.md).
